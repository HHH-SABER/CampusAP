# CampusAP 双端方案（Windows + Android）

> 依据：`CampusAP` 源码评审（5 份并行评审 + 主审复核）、`02_逆向样本` 四个 PC 样本与两个安卓样本的静态分析、
> 以及 VPNHotspot / PocketRouter / AOSP 等外部参考。所有结论标注了出处，未验证项显式标为「待实测」。
> 本文是方案，不是施工记录；代码未改动。

---

## 0. 定位：两端不是「同一软件的两个版本」

| | Windows 端 | Android 端 |
|---|---|---|
| 网络角色 | 把 **PC** 变成共享网关 | 把 **手机** 变成共享网关 |
| 上游 | 校园网（有线/无线 + Portal/802.1X） | 校园网（WiFi + Portal） |
| 下游 | 系统移动热点（WinRT Tethering） | 系统热点（Tethering） |
| 护城河 | **免驱**（竞品全是内核驱动 + 网卡白名单） | **免装客户端**（客户端浏览器即可管理） |
| 真正的难点 | 宿主认证保活 + 按设备管控（已判定不可行） | 宿主认证保活 + 高版本权限墙 |
| 可管控性 | ❌ 原理性不可行（winnat 双份投递） | ✅ root 下原理性可行（标准 Linux 转发） |

**核心判断：两端的差异化能力不同，不该互相移植架构，但应该共享协议资产与产品规范。**
Windows 端赢在「免驱 + 桌面常驻 + 用户态统计」；Android 端赢在「认证观测面更好 + root 下管控真的可行」。

## 1. 两端能力对照总表

| 能力 | Windows 现状（v0.7.0） | Android 可行性 | 可复用度 |
|---|---|---|---|
| 校园网门户认证（ePortal/Srun/Dr.COM） | ✅ 已实现（`EportalClient`） | ✅ 完全可行，观测面更好 | **高（协议逻辑）** |
| 认证保活看门狗 | ✅ 60 秒轮询 | ✅ 前台服务 + `NetworkCallback`（比轮询更省电更准） | **高（策略）** |
| 热点启停/配置 | ✅ WinRT `NetworkOperatorTetheringManager` | ⚠️ `TetheringManager`(API30+) 或跳系统设置 | 低（平台 API 不同） |
| 热点客户端列表 | ✅ 系统 API（比 ARP 权威） | ⚠️ 无 root 不可靠；Shizuku/root 下 `ip neigh` | 低 |
| 实时流量统计 | ✅ WinDivert 双层（Forward 观察 + Network 计数） | ⚠️ 仅 root（`iptables -nvx -L`） | 无 |
| 按设备限速/拉黑 | ❌ 已移除（不可行） | ✅ 仅 root（`iptables -m mac` / `tc`） | 无 |
| TTL 伪装 | ⚠️ 已实现但**只遮 TCP**、值有 fallback 隐患 | ❌ 无 root 不可行；root 下 `iptables -j TTL` | 无 |
| 免装客户端的管理页 | ✅ HttpListener :8899 + 一次性令牌 | ✅ 同构（可跑同一份 HTML/JS） | **高（页面+API 形状）** |
| 设备命名 / OUI 厂商识别 | ✅ OUI 表 + mDNS + 反向解析 | ✅ 同数据 | **高（数据表）** |
| 单实例 / 托盘 / 悬浮窗 | ✅ | N/A（前台服务 + 通知） | 低 |

## 2. 电脑端方案

### 2.1 现状与定位（结论）

竞品全部是「Realtek/Ralink OEM SoftAP SDK + 自研/半自研 NAT 驱动」的 2014–2018 代方案，靠
「多后端降级链 + 333 条硬件 ID 白名单 + 在线拉驱动」对抗碎片化；自研内核 NAT 在签名政策下已是死路。
**CampusAP 的免驱 WinRT 路线是唯一现代替代，这是它必须守住的定位。**

管控（限速/拉黑）已在 v0.7.0 整体移除，依据是 winnat 连接重定向 + NDIS 双份投递的四轮真机取证
（见 `docs/交接文档.md` §1.5）。**本方案不再沿 WFP 路线修复管控。**

### 2.2 三个工作流

#### A. 质量与稳定性收口（v0.7.1，优先级最高）

已审出、尚未修复的确定性缺陷，按修复成本从低到高：

| 编号 | 问题 | 位置 | 影响 |
|---|---|---|---|
| A1 | `WinDivertOpen` 失败返回 `(IntPtr)(-1)` 而非 0，判据写的是 `IntPtr.Zero` → **全部错误诊断成为死代码**，UI 显示"运行中"但 4 线程空转 | `TrafficEngine.cs:88`、`:196` | 阻断级，已二进制级双路径验证 |
| A2 | Web 管理页在 `HttpListener` 线程枚举 UI 线程的 `ObservableCollection` | `MainViewModel.cs:685` + `WebConsoleServer.cs:53/125` | 偶发 `InvalidOperationException`，响应不关闭致手机页挂起 |
| A3 | 深澜 Srun 的 `info` 字段是字面量双花括号 → 非法 JSON，该门户路径不可用 | `EportalClient.cs:166` | 功能不可用 |
| A4 | `Observe` 的 IPv4 分支 off-by-4：守卫 `len < ihl2+4` 却读 `ReadU32(ihl2+4)` → 读到复用缓冲区的残留字节，产生垃圾 `seq` | `TrafficEngine.cs:297/302` | 污染 pending 表 |
| A5 | `WinDivertBuffer` 从不 `Dispose`（无 `using`），每次开关统计泄漏 4×64 KiB 钉住内存 + `GCHandle` | `TrafficEngine.cs:220/336` | 反复开关持续泄漏 |
| A6 | `Application.Shutdown()` **会**触发 `Closing`（官方文档），代码注释与相交接文档均写反 → 提权重启时弹模态"关闭行为"对话框，与提权实例 5 秒接管窗口竞争 → 静默失败 | `MainViewModel.cs:561`、`MainWindow.xaml.cs:118` | 高危，需真机确认必现/偶发 |
| A7 | 设置/凭据文件非原子写入；`Save()` 在属性 setter 内且无 try/catch；反序列化不校验成员级 null（`{"DeviceNames":null}` → NRE → 进程退出） | `AppSettings.cs:51`、`CampusAccountStore.cs:41`、`MainViewModel.cs:67/821` | 丢配置 / 崩进程 |
| A8 | `run_probe.bat:17-18` 的 NuGet 路径被控制字节破坏（`\1`/`\b`/`\x64`），且 `copy` 无 errorlevel 检查 → README 指引的取证闭环是断的 | `tools/CaptureProbe/run_probe.bat` | 排障工具不可用 |
| A9 | 版本单源在 4 处硬编码；`发布.ps1` 用 `$env:USERPROFILE\.nuget` 而 csproj 用 `$(NuGetPackageRoot)`；全新克隆无 `发布\` 时被误判为"被锁定"并 `exit 0` | `发布.ps1:42/48-51` | 发布不可靠 |

其余中低项（`SetClients` 清空窗口、UDP 流键缺设备维度导致**永久**误归属、TTL 只遮 TCP、IPv6 不遍历扩展头、
日志每次开文件 + `SetClients` 每 2 秒写一条 Info、`MainViewModel` 904 行上帝类、三个 `DispatcherTimer` 无法停止、
`NativeShellExecuteInfo` 两处重复、`_diag.ps1` 与 `_diag_log.txt` 残留、README 与代码大面积漂移）
一并纳入本批次，细则见评审记录。

#### B. 功能补齐（v0.8）

1. **TTL 伪装补完（重要）**：当前只对 TCP 生效（`TrafficEngine.cs:481`），UDP/DNS/QUIC 仍带客户端原始 TTL
   → 与「抹掉多设备指纹」的目标不符。同时修 `ReadHostTtl` 的 fallback：若宿主真实 TTL 是 128 而
   注册表读不到、固定按 64 伪装，**反而制造了新的可区分特征**（"所有客户端都是 64，只有宿主不是"）。
   必须改为「探测宿主真实出向 TTL（统计本机出向包 TTL 众数）」而非假定。
2. **IPv6 补完**：加 Next-Header 链遍历（至少 0/43/60/44），Fragment 非首片停止传输层解析；
   计数与管控入口对齐 v4。
3. **拓扑与归属修正**：`SetClients` 改「局部构建新表 + 原子替换」；UDP pending 键加设备维度；
   `_flows` 增可重估路径（当前一次性创建 + `LastSeen` 续命 → 误归属永不过期，与交接文档所称"短暂错位"不符）。
4. **门户扩展**：
   - `passwordEncrypt=true`（RSA）门户：**不再硬啃**，用内嵌 WebView2 兜底自动填表 + 提交（技术总结 §6.1 已给此结论）
   - `PortalKind.Unknown` 时**拒绝自动提交凭据**（当前静默回落到锐捷协议，见 `EportalClient.cs:131`）
   - 登录前校验目标主机（同网段/网关 IP），非 HTTPS 明确提示
   - 802.1X/EAP 场景调研（360 用 `CiscoEapFast.dll` + `360WifiSchool.dll` 单独成模块，说明这是宿舍场景的真护城河）
5. **设备识别打磨**：主机名关键词→厂商映射（`Mi`/`Redmi`→小米、`Magic`/`Honor`→荣耀），
   修正 `OuiLookup` 的本地管理位地址条目（`FA:AB:7D`/`FE:44:7B` 等不可能是厂商 OUI）
6. **管理页增强**：连接历史、流量曲线、CSV 导出；令牌改 `X-Web-Token` 头 + `Cache-Control: no-store`；
   校验 `Host`（前缀不是网卡绑定，`WebConsoleServer.cs:18` 的注释不成立）

#### C. 管控功能的最终取舍（v0.9，需要拍板）

三条剩余路径，成本收益对比：

| 方案 | 做法 | 效果 | 成本 | 建议 |
|---|---|---|---|---|
| **B1 NDIS 层** | 用 [wiresock/ndisapi.net](https://github.com/wiresock/ndisapi.net)（WinpkFilter 驱动，商业授权约 $200）或自写 NDIS LWF | **唯一能覆盖双份投递**的现成路线，按 MAC 丢包/整形 | 商业授权费，或内核 C + WDK + **EV 证书签名** | 做成**可选插件**，不进主程序 |
| **B2 改拓扑** | 外接 USB 网卡 + ICS（路由型共享），限速点成为唯一网关 | WinDivert 现有代码直接生效 | 需第二块网卡 | 写成**部署指南**，零代码 |
| **B3 网关侧** | 软路由（OpenWrt/OPNsense）集中做 per-device QoS | 效果最好、最稳 | 需额外硬件 | 写成**推荐拓扑** |

**推荐**：主程序保持「统计模式」定位（诚实、免驱、可维护）；B1 作为独立可选分支；B2/B3 作为文档。
理由：主程序的目标用户是"宿舍里用笔记本开热点的人"，让他们为此买驱动授权或第二块网卡不现实；
而「诚实降级 + 明确诊断」已经是这个项目做对的地方（v0.7.0 的 UI 降级就是这么做的）。

#### D. 工程化（贯穿）

- **建测试工程**（当前仓库**零测试**、CI 无 `dotnet test`）。优先可测的纯函数：
  `FixIpChecksum`、IP 头解析边界（A4 正好可测）、`OuiLookup` 表无重复键（曾因 29 个重复键导致全部查询静默失败）、
  `EportalClient.ParseRedirect/DetectPortalKind/ParseLoginResponse`、设置 JSON 往返
- **开分析器**：`EnableNETAnalyzers` + `AnalysisLevel`，`.editorconfig` 加 `dotnet_diagnostic.*.severity`；
  可空性已开（两个 csproj 都有 `<Nullable>enable</Nullable>`）但无 `TreatWarningsAsErrors`
- **发布链路**：代码签名（当前 exe/安装包均未签名）；`apply_update` 改内置更新器或校验哈希/签名
  （当前从 exe 上级目录执行未校验的 `.bat`，且主程序常以管理员运行 → 本地提权面）
  —— 可评估 [Velopack](https://github.com/velopack/velopack)（见附录 A.1），一次消掉 A9 与 M14/M15 并支持签名
- **提权分层（建议纳入，需拍板）**：把「整个程序以管理员重启」改为「仅一个只做采集的 daemon 提权，
  UI 常驻普通权限」（参考 [Net-Vanguard](https://github.com/aaron-fredrick/Net-Vanguard) 的命名管道双进程架构，附录 A.1）。
  一次调整同时缓解 A6（重启竞态）、M14（提权面）与 §2.2 D 的上帝类问题
- **文档纠错**：README 全量漂移（限速/拉黑/令牌桶/TTL=129/双层抓包模型）、
  CHANGELOG 0.7.0 条目自相矛盾、`_stagingersion.txt` 转义损坏、交接文档 §7.2 的
  「`Shutdown()` 不触发 `Closing`」**错误结论已变成代码 bug（A6）**

## 3. 安卓端方案

### 3.1 现状：两个样本都不是 WiFi 共享软件（关键发现）

| 样本 | 包名 | 真实身份 | 决定性证据 |
|---|---|---|---|
| `wifigx.apk` | `com.youan.universal` 4.7.5 | 上海游安（**= WiFi共享大师同厂**）的 **WiFi 万能钥匙 + 广告变现** | 无 `BIND_VPN_SERVICE`/`NET_ADMIN`/`TETHER_PRIVILEGED`；`hotspot`/`tether` 关键词零命中；组件为幸运转盘/积分/流量兑换/直播打赏；重广告栈；`usesCleartextTraffic=true`；**已加固**（`assets/39285EFA.dex` 校验和破坏 + `appComponentFactory="."`） |
| `WiFi助手_1.apk` | `app.xiaofeng.android` 2.0 | 小逢智能（**= WiFi助手_1.exe 同厂**）的**换皮 OpenVPN 客户端** | Application = `net.fastvpn.openvpn.OpenVPNApplication`；`OpenVPNService` + `android.net.VpnService`；`AppList` 分应用代理；~80 语言（ics-openvpn 血统） |

**结论：安卓端"竞品"没有可借鉴的共享架构。** 但它们反证了一件事——CampusAP 的价值主张
（**校园网认证保活** + **免装手机客户端的管理页**）恰好是它们都没做的差异化点。

### 3.2 三档能力矩阵（功能随权限自动降级）

| 能力 | 无 root | 有 Shizuku（ADB shell 身份，Android 11+ 无线调试） | 有 root |
|---|---|---|---|
| 校园网门户认证 | ✅ | ✅ | ✅ |
| 认证保活看门狗 | ✅ | ✅ | ✅ |
| 一键开关/配置系统热点 | ⚠️ `TetheringManager`(API30+) 或跳系统设置 | ⚠️ hidden API 反射 | ✅ |
| 热点客户端列表 | ❌ 不可靠 | ⚠️ `ip neigh`/`dumpsys` 尽力而为 | ✅ `ip neigh`/`ndc ipfwd` |
| 按设备流量统计 | ❌ | ⚠️ `iptables -nvx -L` 读计数 | ✅ |
| 按设备限速/拉黑 | ❌ | ❌（写防火墙通常被 SELinux 拒） | ✅ `iptables -m mac --mac-source` / `tc` / `hashlimit` |
| TTL 伪装 | ❌ | ❌ | ✅ `iptables -j TTL --ttl-set` |
| 免装客户端的管理页 | ✅ | ✅ | ✅ |

**Android 特有的两个关键事实（来自活跃项目与 AOSP）**：
1. 普通 App **不能**修改系统热点的 DHCP 池/网关/NAT/防火墙/客户端隔离（[PocketRouter](https://github.com/fiozxr/PocketRouter) 明确列出）；
   `LocalOnlyHotspot` 公共 API **不共享互联网**。
2. **tethering 硬件卸载（offload）会让软件路径失效**，需要关闭 `tether_offload_disabled`
   （[VPNHotspot](https://github.com/Mygod/VPNHotspot) README 记为"必须"）。
   ——这是 Windows "双份投递"的 Android 版，**但 Android 有官方开关可关，Windows 没有**。这正是 Android(root) 可行的原因。

### 3.3 架构（三模块，与电脑端的上帝类拆分一一对应）

```
CampusAP-Android/  (Kotlin + Jetpack Compose, minSdk 26)
├── CampusAuthService   ← 移植 EportalClient：门户探测/识别/POST 登录/重登
│                         + ConnectivityManager.NetworkCallback
│                           （NET_CAPABILITY_CAPTIVE_PORTAL / VALIDATED）
│                         + 前台服务看门狗
├── HotspotController   ← TetheringManager 封装 + 三档能力探测（对应 Windows 的 CheckCapability 8 种诊断）
├── ClientMonitor       ← 可选：Shizuku/root 下 ip neigh + iptables -nvx -L + tc -s
└── WebConsole          ← 同构管理页（同一份 HTML/JS + 同一套 API 形状）
```

**从电脑版血泪史继承的四条纪律**：
1. 能力探测失败**必须显式告警，绝不静默失效**（电脑版最后做对了这点）
2. **更新/提权绝不用外部脚本**（电脑版那个本地提权面就是这么来的）
3. 凭据用 `EncryptedSharedPreferences`/Keystore；`networkSecurityConfig` 白名单，**不请求 `REQUEST_INSTALL_PACKAGES`**
4. TTL 伪装/限速默认关闭并给合规提示

### 3.4 安卓端里程碑

| 里程碑 | 内容 | 是否需 root | 能否独立发布 |
|---|---|---|---|
| M1 | 校园网一键认证 + 掉线保活 | 否 | ✅ 可单独发布 |
| M2 | 一键开热点 + 配置 + 手机浏览器管理页 | 否 | ✅ **M1+M2 = 完整可发布产品** |
| M3 | 客户端列表 + 只读流量统计（Shizuku 尽力而为） | 否（Shizuku） | ✅ 增量 |
| M4 | 按设备限速/拉黑 + TTL 伪装（root 专属） | 是 | ✅ 作为"高级模式" |

**建议先做 M1+M2**：完全不需要 root，恰好绕开 Android 的权限墙，且已构成对那两款样本的差异化产品。

## 4. 双端复用与工程协同

### 4.1 可复用资产清单

| 资产 | 复用方式 | 复用度 |
|---|---|---|
| 门户认证协议逻辑 | 抽「门户适配器」规格（探测→识别→登录→重登），两端各自实现，**共享 golden 测试向量**（录制的 HTTP 交互） | 高 |
| 认证保活策略 | 共享策略文档（queryString 有时效，每次重登现抓；`passwordEncrypt=true` 走 WebView 兜底） | 高 |
| Web 管理页 HTML/JS | **同一份页面**，两端都是 `GET /`（内嵌令牌）+ `GET /api/devices?token=` | 高 |
| OUI 厂商表 | 抽成一份 `oui.json`，两端打包（同时修本地管理位地址问题） | 高 |
| 设备命名优先级规则 | 共享规则：自定义名 > mDNS 名 > 厂商+型号 > 主机名 > IP | 高 |
| 版本/CHANGELOG/上传规制 | 共享工程规范（版本单源、Keep a Changelog、提交前红线自查） | 高 |
| 抓包/统计/管控 | **不可复用**（WinDivert ↔ iptables/tc 完全不同） | 无 |
| 热点启停 | 不可复用（WinRT ↔ TetheringManager） | 无 |

### 4.2 仓库策略（需拍板）

- **方案甲（推荐）**：单仓库 `CampusAP/` 下增 `android/` 子目录，共享 `docs/`、`oui.json`、`webconsole/`（页面与 API 契约）
  —— 好处：契约变更一次提交两端同步；坏处：CI 需要分 job
- **方案乙**：拆两个仓库，用 git submodule 共享 `shared/`
  —— 好处：发布独立；坏处：契约同步靠人肉

### 4.3 管理页同构（具体做法）

把当前内嵌在 `WebConsoleServer.cs` 的 HTML 提出来成独立文件，作为**双端共享的契约**：
- API：`GET /`（发令牌）、`GET /api/devices?token=`（设备+速率）
- 安卓端把 `HttpListener` 换成 NanoHTTPD/Ktor，页面与字段名一字不改
- 未来加写端点（如断开设备）时，两端同时加鉴权与 `Host`/`Origin` 校验（当前只有只读 GET，风险有限）

### A.1 架构级 —— 最该优先读（3 个）

**1. ✅ [Net-Vanguard](https://github.com/aaron-fredrick/Net-Vanguard) — 权限分离双进程架构**

C# 12 / .NET 8。README 自述 "Analyzes network traffic natively at the kernel level **without injecting drivers or resorting to external packet sniffers**"（即用 ETW）。

```
NetVanguard.Daemon  ← 管理员权限，仅它提权：ETW 采集 + 防火墙 COM (HNetCfg.FwPolicy2)
      ↕ 命名管道 TrafficPipe / CommandPipe
NetVanguard.App     ← 普通用户权限的 UI，ObservableCollection 聚合展示
```

**对 CampusAP 的意义（本附录里最大的一条）**：当前是「开统计 → **整个程序** UAC 重启成管理员」，由此产生三个连带问题：

- **体验**：重启后托盘 / 悬浮窗 / 热点状态需重建，并与提权实例的 5 秒接管窗口竞争（缺陷 A6）；
- **安全**：**正因为整个进程都是管理员**，`MainViewModel.CheckStagingVersion` 从 exe 上级目录执行未校验的 `apply_update.bat` 才构成本地提权面（M14）；
- **可维护**：提权 / 驱动 / 采集逻辑与 UI 混在 904 行的 `MainViewModel` 里。

收敛为「仅 daemon 提权」可同时缓解三者，并与 §2.2 D 的"拆上帝类"、§3 的三模块划分同构。另可借：SQLite 持久化历史流量（对应 §2.2 B.6 的历史 / 曲线）、LiveCharts2 图表。

**2. ✅ [Velopack](https://github.com/velopack/velopack) — 安装与自动更新框架**

README 核实：一条命令产出**安装包 + 更新包 + delta 增量包 + 自更新便携版**；Rust 实现；**"integrates easily with code signing"**；支持 C# / C++ / JS / Rust；可从 Squirrel.Windows 自动迁移。

**替代对象**：`发布.ps1`（硬编码 NuGet 路径、全新克隆被误判"被锁定"、`exit 0` 掩盖失败 → A9）+ `apply_update.ps1`（无条件自提权）+ 未校验的 `apply_update.bat`（M14 / M15）。走签名更新包 + 内置更新器，可一次消掉"发布链路三处重复"与"本地提权面"。代价是接受 Squirrel 式 `current/` 目录约定。

**3. ✅ [wiresock/ndisapi.net](https://github.com/wiresock/ndisapi.net) — §2.2 C 方案 B1（NDIS 层）的现成 C# 接口**

README 核实：Windows Packet Filter 驱动的 .NET 封装；能力为枚举网卡、`SetAdapterMode`（TUNNEL / LOOPBACK_FILTER / LOOPBACK_BLOCK）、`SetPacketEvent` 事件驱动收包、过滤 / 改包 / 发原始包。官方示例直接 `using PacketDotNet;`。

这是"管控终审"里**唯一能覆盖 NDIS 双份投递**的路线。许可分工：**.NET 封装 MIT，驱动本体（ntkernel.com Windows Packet Filter）商业授权** —— 这正是把 B1 做成"可选插件"而非主程序依赖的原因。
