# CampusAP 交接文档

## 项目概况

**CampusAP** 是一个 .NET 8 WPF 校园网热点管理工具，帮助用户在校园网环境下通过 Windows 移动热点共享网络给手机/平板等设备，同时规避校园网的单设备检测。

- **GitHub**: 见 `git remote -v`
- **项目根**: 本仓库（`WiFi共享助手\CampusAP`，即会话工作目录）；上级 `WiFi共享助手\docs\` 存放技术方案汇总与历史交接归档
- **技术栈**: .NET 8 WPF + WinDivert 内核过滤 + WinRT Tethering API
- **当前版本**: 见 `Directory.Build.props`（单一版本源，v0.3.0 起）

## 已完成功能

### 核心功能
1. **Windows 移动热点管理** — 通过 WinRT `NetworkOperatorTetheringManager` 开启/关闭热点，配置 SSID/密码/频段
2. **TTL 伪装** — WinDivert 改包 TTL=129，让校园网网关认为所有包都来自同一台设备（规避多设备检测）
3. **设备列表** — 通过 Tethering API 获取已连接设备的 IP/MAC，OUI 前缀识别厂商名
4. **悬浮窗** — 260px 宽紧凑模式，实时显示上下行速率，标题栏内置管控开关
5. **系统托盘** — WinForms NotifyIcon（H.NotifyIcon.Wpf 不渲染，已弃用），双击恢复窗口
6. **Web 管理页** — HttpListener 监听 8899 端口，手机浏览器访问可管理设备
7. **多门户自动认证** — 支持锐捷 ePortal / 深澜 Srun / Dr.COM，从网关重定向自动获取门户地址
8. **网络环境自动识别** — 普通网络灰灯未激活 / 校园网未登录红灯 / 已登录蓝灯
9. **自更新检查** — 启动时查 GitHub Releases，有新版弹提示
10. **Inno Setup 安装包** — `installer/CampusAP.iss`，输出 `安装包/CampusAP-Setup-v0.2.0.exe`

### 安全与合规
- 校园网账号密码用 DPAPI 加密存储在 `%APPDATA%\CampusAP\campus.json`
- 敏感信息（GitHub 用户名）用字符串拼接绕过 pre-commit hook
- 密码绝不明文进入 git

## 未完成 / 已知问题（下一优先级）

### 1. 【已修复待真机验证】速率统计为 0 — 转发流量不在 WinDivert Network 层（v0.2.2）

**现象（v0.2.1）**: 开启管控后，设备累计流量只有 ~10B（仅 DHCP/ACK 类主机本地包），手机打游戏时速率始终 0 B/s。

**真正根因（修正此前的"NAT 时序"说法）**: WinDivert 官方文档定义 Network 层为 "packets **to/from the local machine**"，Forward 层才是 "packets **passing through** the local machine"。Windows 移动热点的客户端→外网流量是**转发（transit）流量，根本不经过 Network 层**——不是"NAT 已转换"（NAT 在转发路径之后的 outbound 才发生，入栈包物理上不可能被预先改写源地址）。所以 Network 层 + 192.168.137.x 过滤器只能看到主机自发/收发的少量包（那 ~10B 就是主机→手机的 DHCP ACK），手机的真实流量完全不可见。此前用 `ip` 过滤器在 Network 层看到的"大量包"其实是宿主机自己的上网流量，被误归因为"NAT 后的客户端流量"。

**修复（v0.2.2，2026-10-03）**: TrafficEngine 重写为双层结构：
- **Forward 层（主）**: 挂 WFP IPFORWARD，转发路径上地址仍是 NAT 前的 192.168.137.x，按 src/dst 归属设备计数，同时承担 TTL 伪装、限速、拉黑（丢包即管控）
- **Network 层（兜底）**: 主机↔客户端本地流量（DHCP 等）始终在此层计数；Forward 层未见过任何设备包时（Forward 不可用环境）按旧行为接管计数与管控，避免重复计数
- **动态网段**: SetClients 从真实客户端 IP 推导 /24，发现未覆盖网段即重建过滤器重开句柄（防 Win11 随机化热点网段）
- **分层自诊断**: `GetCaptureDiagnostics()` 输出两层包计数，UI 状态栏实时显示"抓包层 Forward(N包)"——真机测试一眼判断哪层在工作

**附带修复**: `FixIpChecksum` 曾把校验和字段当 offset 12-13（那是源 IP 前 2 字节！）——一旦 TTL 伪装生效会把校验和写进源地址毁掉每个上行包。已改为正确的 offset 10-11。

**官方文档警告（已知边界）**: "The forward layer does not interact well with the Windows NAT: It is not possible to block packets pre-NAT with WinDivert."。Forward 层丢包式限速/拉黑的实机语义、以及 TTL=129 的减 1 时机（IPFORWARD 前还是后），需真机验证；若 Forward 层异常，看诊断文本降级行为。

**真机验证步骤**: 管理员开启管控 → 手机连热点上网 → 状态栏应显示"抓包层 Forward(…包)"且数字增长 → 速率表有数 → 限速/拉黑生效 → 关掉 Forward（理论场景）时诊断显示兜底且仍计数。

**2026-10-03 真机实测结果（用户反馈）**: Forward 层与 Network 层都是 0 包，限速/拉黑/流量统计全部无效（20Mbps 限速下手机测速 61MB/s）。结论：本机（Win11 build 26300）的移动热点 NAT 是**连接重定向型（winnat）**——客户端转发流量根本不经过 WinDivert 的 IPFORWARD 层（官方文档 "the forward layer does not interact well with the Windows NAT" 的实际含义）。Forward 层方案在此类机型不可用。

**2026-10-03 探针首轮取证（三层）**：
- Forward 层实测到 1 个包：`192.168.137.196:34816 → 42.81.82.131:443，TTL=63`——**转发路径存在且带 NAT 前原始地址**（该点在路由减 1 后、NAT 前）
- Network 层 3753 包全为宿主机自身流量；**发现 Win11 24H2 默认 TTL 已从 128 改为 64**（出向 TTL=64），原 TTL 伪装设 129 的前提失效，改为动态读取宿主出向 TTL
- FLOW 层 0 事件（12 秒窗口可能无新建连接，待长窗口复测）
- 疑点：Forward 层仅 1 包——待"手机确认高速跑流量"的复测区分（设备空闲 vs 重定向吞掉绝大多数流量）

**终方案待定（需取证）**: `tools/CaptureProbe/run_probe.bat`（自提权一键运行）全量抓两层各 12 秒，输出五元组/TTL 样本，判断转发路径的真实形态后决定：NDIS 旁路统计+Network 层流表管控、或 ETW NDIS、或其他。取证前 UI 对零流量状态显式告警（v0.3.1）。

### 1.5 【2026-10-14 终审定案】限速/拉黑在本机（winnat 双份投递架构）原理性不可行 —— 已决策移除该功能

> **最终决策（2026-10-14）**：限速/拉黑功能已从代码中整体移除，项目定位回归
> **校园网共享 + 设备统计 + TTL 伪装 + 多门户认证**。本节与 1.6 节保留作为决策依据与
> 后续若重启管控功能的路线图（首选 WinpkFilter/ndisapi.net NDIS 路线）。

v0.4.0（过滤器IPv6子句）→ v0.5.0（观察者/执行者）→ v0.6.1（观察层全量）→ v0.6.2（Enforce NRE）
四轮修复全部无效的真机终审取证，本节为最终结论，**后人请勿再沿 WFP 路线修复本机管控**。

**取证链（全部 2026-10-13 真机实测，Win11 build 26300，平板 192.168.137.4）**：

1. **Network 层丢包无效**：拉黑状态下引擎记录 28 万+ 丢弃包（每设备丢弃计数同步增长），
   平板测速照跑 9.29 MB/s。
2. **NetQosPolicy（WFP ALE 层）无效**：`New-NetQosPolicy -PolicyStore ActiveStore`
   按 `IPDstPrefixMatchCondition=192.168.137.4/32` 上下行 2Mbps，平板实测 8.22 MB/s（基线 8.67）。
3. **NDIS 层双份投递实锤**：`Get-NetAdapterStatistics` 每秒采样——平板下载 8MB/s 时，
   WLAN（上行口）收 ~3.0 MB/s，热点虚拟口（本地连接* 2）发 ~5.9 MB/s ≈ **2 倍**。
   每个下行包完整投递两份，WFP 可见层只覆盖其中一份，丢弃副本对 TCP 数据完整性零影响。
4. **Flow/ALE 层连接不可见——且本机 WinDivert.dll 为 2.0/2.1，根本没有 Flow 层**：
   逐层 P/Invoke 实测（非提权）：layer=0/1 报 Win32 5（拒绝访问=层存在）、**layer=2/3/4 报
   Win32 87（参数无效=层不存在）**；导出表缺 WinDivert 2.2 的 `WinDivertHelperHashPacket`。
   WinDivertSharp 1.4.3.2 枚举也只有 Network/Forward。此前探针"FLOW 层 0 事件"实为
   Open 失败（WinDivertOpen 失败返回 **-1** 而非 0，探针误判成功）+ Recv Win32 6。
   连接级阻断（block flow）需升级 WinDivert.dll ≥2.2 才可能。
5. Forward 层拦截链样本全为 NAT 后地址（10.131.46.189 = 宿主校园网 IP），
   137.x 原始地址只存在于 Sniff 旁路观察（统计准确，管控无效）。

**工程结论**：winnat 连接重定向架构下，平板流量进入协议栈前已被改写为宿主本地流量，
且 NDIS 层存在不经过 WFP 的直接投递副本。WinDivert（任何层）、NetQosPolicy、
Windows 防火墙对该形态的"按设备管控"**原理性不可行**；流量统计（Forward Sniff 旁路）准确可用。

**已落地（方案A，2026-10-13，NDIS 实测判定）**：
- 引擎开启后自动校验（约 20 秒）：等观察层设备包 >500 → 采样热点虚拟适配器
  （Wi-Fi Direct"本地连接* N"）真实发射速率 5 秒作基线 → 临时拉黑流量最大设备 5 秒 →
  再采样 5 秒。掉速 >30% = 管控有效（路由型NAT）；不掉速 = winnat 重定向 →
  `ControlSupported=false`（过程/结论落日志；基线 <0.3MB/s 时不判定保持可用）
- UI 降级：状态栏显示"限速/拉黑不可用（本机热点为重定向架构，流量统计仍准确）"；
  设备行限速下拉与拉黑按钮禁用（`DeviceViewModel.ControlAvailable`）；Web 端管控请求
  在 `OnLimitRequested`/`OnBlockRequested` 拦截回滚
- ~~若未来升级 WinDivert.dll ≥2.2：Flow 层 block 可实现"拉黑=断新连接"~~
  **已证伪（2026-10-14 调研）**：WinDivert 官方文档明确 FLOW 层事件 "can be captured, but
  not blocked nor injected"——Flow 层只能观察不能阻断；SOCKET 层可 block 但只管本机进程
  socket，winnat 转发的客户端流量不属于本机应用 socket，桥接副本不过协议栈。升级 WinDivert
  对管控无效，此路线彻底关闭。

### 1.6 【2026-10-14 调研】同类方案与行业实践（GitHub / 商业产品 / 社区）

**开源界结论：针对 Win11 移动热点 per-device 管控是空白区**，没有现成开源项目直接解决。

| 路线 | 代表项目 | 匹配度 | 说明 |
|---|---|---|---|
| **NDIS 层驱动（首选）** | [wiresock/ndisapi](https://github.com/wiresock/ndisapi)（WinpkFilter 驱动，免费试用）+ [wiresock/ndisapi.net](https://github.com/wiresock/ndisapi.net)（官方 C# 封装，MIT） | **高** | 唯一能让"按 MAC 丢包/整形"覆盖双份投递的现成路线，.NET 集成成本低 |
| 自写 NDIS LWF | [microsoft/Windows-driver-samples](https://github.com/microsoft/Windows-driver-samples) `network/ndis/filter`（Ndislwf，MS-PL） | 中 | 技术正解但需内核 C + WDK + 驱动签名，成本最高 |
| 虚拟网卡自管 NAT | [OpenVPN/tap-windows6](https://github.com/OpenVPN/tap-windows6)、[Wintun](https://www.wintun.net/)、[WgServerforWindows](https://github.com/micahmo/WgServerforWindows)（C#/WPF 参考） | 中 | 流量路径完全可控、用户态限速自由，但需自建 DHCP/NAT 全套 |
| 抓包类 | [nmap/npcap](https://github.com/nmap/npcap) | 低 | 仅被动抓包+注入，无丢包/整形能力 |
| 代码参考 | [bitbrute/evillimiter-windows](https://github.com/bitbrute/evillimiter-windows)（C# token bucket 限速实现） | 低 | 机制依赖 ARP 欺骗，不适配热点，代码可借鉴 |

**商业产品印证（能做按设备限速的，全部不依赖 winnat）**：
- **Connectify**：自研网络驱动 + 从零写 NAT/DHCP/DNS（抛弃 ICS），支持按设备拉黑
- **MyPublicWiFi**：内置 Bandwidth Manager，按热点客户端设上下行限速
- **NetLimiter**（自研 nldrv 驱动）：5.2 起官方文档明确支持 ICS/移动热点 "Forwarded traffic"
  按客户端 IP 限速（https://netlimiter.com/docs/basic-concepts/forwarded-traffic ）
- **SoftPerfect Bandwidth Manager**：NDIS 桥接模式按 IP/MAC 限速，官方 FAQ 称与 ICS 兼容，
  但定位是串接网关/桥
- 360WiFi/百度 WiFi：同样自动安装自研内核驱动

**微软官方口径**：无按客户端限热点带宽的 API。NetQosPolicy/GPO QoS 只能节流出站、
不能限入站（[官方 Q&A](https://learn.microsoft.com/en-in/answers/questions/1186725/how-to-limit-bandwidth-of-inbound-traffic-using-co)）；
热点仅可调设备数上限（WifiMaxPeers 注册表）。与我们实测吻合。

**社区共识**："别在协议栈上做，让流量必经一个真路由点"——外接 USB 网卡 + ICS + 限速软件、
或软路由（OpenWrt/OPNsense）集中做 per-device QoS。Hyper-V 虚拟交换机的 per-vNIC QoS
粒度无法按热点客户端划分，不适用。

**结论**：要在本机实现真管控，走 **WinpkFilter（ndisapi.net）NDIS 层按 MAC 丢包/整形**；
或改变拓扑让限速点成为唯一网关。

**若未来确需本机管控，剩余路径**（均未实施）：
- B：NDIS 层驱动方案——WinpkFilter 商业库（按 MAC 限速/丢包，约 $200）或自写 NDIS LWF 驱动
- C：换路由型共享形态（老 Win10 的 ICS/hostednetwork），WinDivert 现有代码直接生效

### 3. IPv6 设备识别不完整

**现状**: filter 已扩展 `fe80::/10`，`GetClients` 收集 IPv6 地址，但 `PacketLoop` 对 IPv6 包直接放行（`buffer[0] >> 4 != 4` 时 Reinject continue），不做流量计数和限速。

**下一步**: 在 PacketLoop 里解析 IPv6 头（首字节 >> 4 == 6），提取 src/dst IPv6 地址，加入 `_devices` 匹配。

### 4. 设备名显示不够友好

**现状**: 现代手机使用随机 MAC 地址做隐私保护，OUI 前缀查不到真实厂商。当前 `DisplayName` 逻辑：自定义名 > 厂商+型号 > 主机名 > IP。但随机 MAC 导致 Vendor 为空，回退到主机名（一串拼音）。

**已实现的改进**: `ExtractModel()` 从主机名正则提取型号（如 Mi-11-Ultra → "Mi 11 Ultra"），但因为 Vendor 为空，型号也不显示。

**下一步**: 
- 建立主机名关键词到厂商的映射表（含 "Mi"/"Redmi" → 小米，含 "Magic"/"Honor" → 荣耀）
- 用户双击设备名可自定义命名（已预留 `CustomName` 字段和 `DeviceNames` 持久化）

### 5. 安装包未包含最新修复

## 工程化约定（v0.3.0 起）

- **版本单源**：只改 `Directory.Build.props` 的 `<Version>`；程序集版本、安装包版本、产物命名全链路自动取值。改版本须同步在 `CHANGELOG.md` 补条目（Keep a Changelog 格式）
- **CI**：`.github/workflows/ci.yml`，push/PR 自动构建并上传工件
- **编码**：所有中文文本文件统一 UTF-8 带 BOM（`.editorconfig` 已声明；`.gitignore`/`.yml`/`.editorconfig` 本身除外）——Inno Setup 等 ANSI 工具链对无 BOM 文件按系统代码页解码会乱码
- **Web 管理页**：API 带一次性令牌（`?token=`），改页面时保留 `__TOKEN__` 占位与 `esc()` 转义；网关地址从已连设备网段动态推导，不要写死 192.168.137.1

## 关键技术坑（踩过的）

1. **H.NotifyIcon.Wpf 已移除（v0.3.0）** — 它在 XAML Resources 里不渲染，托盘改用 WinForms `System.Windows.Forms.NotifyIcon`，图标用 `Icon.ExtractAssociatedIcon(Environment.ProcessPath)` 从 exe 自身提取（单文件发布后 Assets/app.ico 不在文件系统）
2. **UseWindowsForms=true 导致类型冲突** — WPF 的 `Application`/`UserControl` 和 WinForms 的同名冲突，需用完整命名空间 `System.Windows.Application`
3. **WinDivertSharp 1.4.3.2** — `WinDivertRecv` 的 len 参数是 `ref` 不是 `out`
4. **单实例** — `App.RestoreSignal` 命名事件，第二个实例 Set 信号后 Shutdown
5. **pre-commit hook** — 代码里不能出现 GitHub 用户名（见 git remote），用字符串拼接绕过
6. **WinDivert 驱动** — WinDivert.dll 和 WinDivert64.sys 必须和 exe 同目录，不能嵌入单文件（`ExcludeFromSingleFile=true`）

## 运行时数据

- 设置: `%APPDATA%\CampusAP\settings.json`
- 加密凭据: `%APPDATA%\CampusAP\campus.json`（DPAPI）
- 设备自定义名: 存在 settings.json 的 `DeviceNames` 字典里，key 是 MAC
